# Software evolution log

This document tells the story of how this project actually evolved: what was built in each phase,
in what order, and — most importantly — every deviation, gotcha, and decision discovered along the
way that isn't derivable just by reading the current code. It exists so a new session (human or AI)
can resume the work without having to rebuild that context from scratch, and so hard-won lessons
(a Ruby constant collision, a Windows file-mode quirk, a flaky-test root cause) don't get
rediscovered the hard way a second time.

For the current architecture (data model, technical decisions, file layout, product scope), see
[`CLAUDE.md`](../CLAUDE.md) at the repo root — that file is the living design reference; this one
is the history of how the app got from nothing to its current state, phase by phase and change by
change.

This file is what `CLAUDE.md` points sessions to for "what's actually implemented and how it
evolved." It consolidates and supersedes `docs/progress.md`, `docs/events-plan.md`, and
`docs/railway-deploy-plan.md` (each an original write-before-execute design doc/execution log,
since deleted — their still-relevant reference content was folded into `CLAUDE.md`, and their
historical narrative lives here).

## Phase 2 — Driver/truck registration

### What was created

- **ActiveRecord::Encryption**: keys generated via `bin/rails db:encryption:init` and stored in
  `config/credentials.yml.enc` (single file, not split per environment). Needed before `Driver`
  could exist, since `cpf`/`phone` are encrypted at rest.
- **Models**: `Driver` (`name`, `cpf` encrypted+deterministic, `phone` encrypted+deterministic,
  `notification_channel` enum `sms`/`whatsapp`/`both` default `sms`, `active`); `Truck` (`plate`
  unique/normalized, `model`, `capacity` validated `> 0`, `active`); `DriverTruck` join model,
  unique on `[driver_id, truck_id]`; `has_many :trucks, through: :driver_trucks` on `Driver` gives
  a free `truck_ids=` writer, used by the driver form's checkbox list.
- **Policies**: `DriverPolicy`, `TruckPolicy` — allow index/show/create/update/destroy to `admin`
  or `cadastro`, deny everyone else, following `ApplicationPolicy`'s deny-by-default base.
- **`ApplicationController`**: now `include Pundit::Authorization` +
  `rescue_from Pundit::NotAuthorizedError` → redirect to `root_path` with an alert. First phase to
  actually wire Pundit into the request cycle.
- **Routes/controllers**: `namespace :cadastro do resources :drivers; resources :trucks end`.
  `Cadastro::BaseController` only handles `authenticate_user!` — the role gate is Pundit's
  `authorize`/`policy_scope` alone, including on `index` (`authorize Driver` before
  `policy_scope`, otherwise an unauthorized role would get a 200 with an empty list instead of a
  redirect).
- **Views**: plain ERB CRUD views under `app/views/cadastro/{drivers,trucks}/`. Driver form has a
  `collection_check_boxes :truck_ids` to assign trucks directly.
- **Factories/specs**: `Driver`/`Truck`/`DriverTruck` factories (using `CPF.generate` for valid
  unique CPFs); model specs, policy specs (`pundit-matchers`' `permit` matcher), request specs per
  controller covering unauthenticated (302), wrong-role (302), and authorized cases.

### Deviations / decisions discovered during execution

- **No `Cadastro::DriverTrucksController`** — pairing management folded into the driver form via
  `truck_ids=` rather than a separate CRUD screen/policy for `DriverTruck`.
- **`DriverTruck#active` isn't exercised yet** at this point — the `truck_ids=` writer
  hard-deletes unchecked pairs rather than soft-disabling them. This mattered once `Visit` existed
  in Phase 3, where `CheckInService`'s upsert finally exercises the soft-disable semantics.
- **`cpf_cnpj` gem has no Rails validator built in** (only `CPF`/`CNPJ` plain Ruby classes) — added
  a custom `validate :cpf_must_be_valid` calling `CPF.valid?` rather than a one-line
  `validates :cpf, cpf: true`.
- Deterministic encryption (`encrypts :cpf, deterministic: true`) was necessary so that
  `validates :cpf, uniqueness: true` and the DB unique index actually work — non-deterministic
  encryption produces different ciphertext each time, breaking both.

## Role key rename — Portuguese → English identifiers

After Phase 2 shipped, `Role::KEYS` and everything derived from it were renamed from Portuguese to
English, since role keys are code identifiers, not user-facing text (the `name` column stays
pt-BR, since that *is* user-facing):

| Old key | New key |
|---|---|
| `cadastro` | `registration_operator` |
| `expedicao` | `expedition_operator` |
| `fila` | `queue_operator` |
| `admin` | `admin` (unchanged) |

Everything mirroring these names was renamed to match: `Role::KEYS`/`db/seeds.rb`'s `ROLES` hash
keys; the `Cadastro::` namespace → `Registration::` (controllers, views, specs, routes, path
helpers); `DriverPolicy`/`TruckPolicy`'s private `cadastro_or_admin?` → `registration_or_admin?`;
all `role?(:cadastro)`/`role?(:fila)` call sites and spec factory traits; `docs/plan.md` updated
throughout. A reversible data migration
(`db/migrate/20260713215625_rename_role_keys_to_english.rb`) updated existing seeded rows in
dev/test, since a plain code change wouldn't have touched them and `Role::KEYS`'s inclusion
validation would have started rejecting the old values.

Verified: `bundle exec rspec` (55 examples, 0 failures) after the migration ran in both
`development` and `test`.

## Phase 3 — Yard check-in

### What was created

- **`Visit` model**: `driver`/`truck` belongs_to, `checked_in_by`/`order_issued_by`/`finished_by`
  audit `belongs_to :class_name "User"` (the latter two `optional: true`), `status` enum
  (`in_yard`/`queued`/`loading`/`finished`, default `in_yard`), `entered_yard_at` required.
  Implemented `active_queue` scope and `queue_position` exactly as designed in `docs/plan.md`, even
  though nothing calls them until the dispatch/queue screens exist — building them alongside the
  model avoided revisiting this file twice.
- **Validation**: "only one active visit (`in_yard`/`queued`/`loading`) per truck and per driver at
  a time," as two custom validations excluding the record's own `id` (so later phases can
  transition an existing visit's status without self-conflicting). pt-BR error messages added.
- **`Visits::CheckInService`** — the app's first service object. Upserts the `DriverTruck` pairing
  (creates it if missing, **reactivates it if soft-disabled**) before creating the `Visit`. This is
  where the `DriverTruck#active` soft-disable semantics flagged in Phase 2 finally get used.
- **`VisitPolicy`**: only `index?` and `check_in?` for now — deliberately did not add
  `issue_order?`/`finish?` yet, since those had no controller to authorize until Phases 4/5.
- **`Registration::VisitsController`** (`index`/`create` only — visit cancellation is out of v1
  scope): `create` authorizes via the domain action (`authorize Visit, :check_in?`) and delegates
  to the service.
- **View**: `app/views/registration/visits/index.html.erb` — driver/truck `collection_select`
  dropdowns (any active driver/truck, matching "the check-in service creates the pairing if
  missing") plus the yard table.
- Fixed a Rack deprecation warning (`:unprocessable_entity` → `:unprocessable_content`), applied
  consistently across Phase 2's controllers too.

### Deviations / gotchas discovered during execution

- **Zeitwerk autoload roots are fixed at boot.** The `web`/`worker` containers had been running
  since Phase 2 (no `app/services/` directory existed yet at that boot). Referencing
  `Visits::CheckInService` raised `NameError` — not because the file was wrong, but because
  Zeitwerk never registered `app/services` as an autoload root for the already-running process.
  Fixed with `docker compose restart web worker`. **Any future session that adds a brand-new
  top-level `app/*` subdirectory (the first file under it) needs the same restart.**

## Phase 4 — Dispatch screen

### What was created

- **`Visits::IssueOrderService`**: given a `visit:` (expected `in_yard`) and `order_issued_by:`,
  sets `order_issued_at`/`order_issued_by` and decides the resulting status — `loading` (plus
  `loading_started_at`) if no other visit is currently `queued`/`loading`, otherwise `queued`.
  Returns the (possibly invalid) visit, same convention as `CheckInService`.
- **`VisitPolicy#issue_order?`**: `expedition_or_admin?`. The `Scope` was broadened to any of the
  three operator roles or admin, since `Visit` records are now read by a second screen.
- **`Expedition::VisitsController`**: `index` (domain-action authorize via `issue_order?`, loads
  `@yard_visits` and `@queue_visits`); `issue_order` (member `PATCH`, scoped to `Visit.in_yard` so a
  stale request can't re-issue an order for an already-dispatched visit).
- **View**: yard table with a `button_to ... method: :patch` per row, plus a queue table showing
  `queue_position`.

### Deviations / gotchas discovered during execution

- **Manual curl-based verification hit a CSRF wall unrelated to this phase's code** — reproduced
  identically against the already-working `Registration::VisitsController#create`, so it's a quirk
  of the manual curl approach (masked-token/session-cookie handshake), not a defect in the new
  controller. Verified instead via `bin/rails runner` invoking the service directly against the
  live dev DB, plus the request-spec suite (which exercises the same path correctly through Rails'
  own integration test session).

## Phase 5 — Queue screen

### What was created

- **`Visits::PromoteNextService`**: no-arg `#call` — finds the earliest-issued `queued` visit and
  promotes it to `loading`; returns `nil` (not an error) when there's nothing queued.
- **`Visits::FinishLoadingService`**: sets `status: finished`, `finished_at`, `finished_by`, then
  calls `PromoteNextService` if the update succeeded — promotion is triggered from inside this
  service so it's genuinely automatic per the state machine; the `queue_operator` only ever
  finishes a visit, never separately promotes.
- **`VisitPolicy#finish?`**: `queue_or_admin?` — the third and final domain action.
- **`QueueScreen::VisitsController`** (see deviation below for the module name): `index` (loads
  `@loading_visit`/`@queue_visits`), `finish` member action scoped to `Visit.loading.find(...)`.

### Deviations / gotchas discovered during execution

- **Ruby's core `Queue` class collides with `module Queue`.** `docs/plan.md` originally named this
  namespace `Queue::`, but Ruby's stdlib `Queue` (from `thread`, always loaded) makes
  `module Queue; end` raise `TypeError: Queue is not a module` at load time. Fixed by naming the
  Ruby module `QueueScreen` instead, keeping the user-facing URL at `/queue` via
  `namespace :queue, module: "queue_screen"`. **Any future top-level namespace should be checked
  against Ruby/Rails core constant names** (e.g. `Set`, `Data`, `Process` are similarly reserved).

### How to verify

```bash

docker compose run --rm web bin/brakeman -q                      # 0 warnings
```

Verified manually: `FinishLoadingService` invoked via `bin/rails runner` correctly finished a

## Phase 6 — Public real-time screen

### What was created

- **Turbo/Stimulus/importmap were never actually wired up before this phase**, despite the gems
  being in the Gemfile since Phase 1 — no `config/importmap.rb`, no `application.js`, no
  `javascript_importmap_tags` in the layout. Harmless until now; required for Turbo Streams to
  process incoming broadcasts in the browser. Ran the standard install generators; deleted the
  generated `hello_controller.js` demo stub.
- **`Visit` model**: `PUBLIC_QUEUE_RELEVANT_STATUSES = %w[queued loading finished]` and an
  `after_commit :broadcast_public_queue!` guarded to only fire on transitions into/out of those
  statuses — a check-in (`in_yard` creation) does **not** broadcast.
- **`Public::QueueController#show`** — genuinely public, no `BaseController`/`authenticate_user!`.
- **Route**: `namespace :public do resource :queue, ... controller: "queue" end`, plus
  `mount ActionCable.server => "/cable"` (never previously present).

### Deviations / gotchas discovered during execution

- **`resource :queue` (singular) does not map to a singularly-named controller by default** —
  Rails still looks for `Public::QueuesController` (pluralized) unless `controller: "queue"` is
  passed explicitly.
- **`mount ActionCable.server => "/cable"` was missing from `routes.rb` entirely** — just never
  added, since no prior phase needed a live cable connection. Manually confirmed the mount accepts
  a websocket upgrade.
- **`config/cable.yml` uses the `async` adapter in development/test**, not `redis` — already the
  case since the Phase 1 scaffold (redis only configured for `production`); sufficient for a single
  Puma process in dev.
- **No system spec yet** for the "action in one tab reflects live in another" scenario — deferred
  to Phase 9. Verified the equivalent manually via a real status transition against the live dev DB.

## Phase 7 — Notifications

### What was created

- **`Notifications::Adapters::BaseAdapter`**: interface marker, `#send_message(to:, body:)` raises
  `NotImplementedError`.
- **`Notifications::Adapters::TestAdapter`**: records every message in memory + logs it, instead of
  sending anything real. `self.clear!` resets between specs.
- **`Notifications::Adapters::TwilioSmsAdapter`/`TwilioWhatsappAdapter`**: wrap
  `Twilio::REST::Client`, credentials accepted as constructor kwargs (not read from `ENV` inline in
  `#send_message`) — this is what makes them testable with fixed fake credentials. WhatsApp
  prefixes `to`/`from` with `whatsapp:`.
- **`Notifications::Dispatcher`**: resolves 1 or 2 adapters from `driver.notification_channel`.
  Adapter *class* resolution goes through
  `Rails.application.config.x.notifications.adapter_class || REAL_ADAPTERS.fetch(channel)` — a
  single config override switch for dev/test (`TestAdapter` for every channel), `nil` in
  production so each channel resolves to its real Twilio-specific class.
- **`Notifications::NotifyDriverService`**: `MESSAGES` hash maps event symbols to message builders
  — only `:your_turn` exists in v1. `.enqueue(visit:, event:)` wraps
  `SendNotificationJob.perform_later`.
- **`SendNotificationJob`**: `retry_on StandardError, wait: :polynomially_longer, attempts: 5`.
- **Trigger points — deliberately in the services, not a model callback**: both
  `Visits::IssueOrderService` (empty-queue case) and `Visits::PromoteNextService` call
  `NotifyDriverService.enqueue` after a successful update.
- **Testing infra added this phase**: `webmock`+`vcr` wired in, `ActiveJob::TestHelper` included
  globally, `config.active_job.queue_adapter = :test` added to `test.rb` (previously every
  environment inherited the global `:sidekiq` adapter — job specs would have silently tried to talk
  to real Sidekiq/Redis).

### Deviations / gotchas discovered during execution

- **Referencing an app/ constant directly inside a `config/initializers/*.rb` file crashed boot**
  with `FrozenError: can't modify frozen Array` inside `Rails::Engine#unshift`. Assigning
  `Notifications::Adapters::TestAdapter` at the initializer's top level forced Zeitwerk to resolve
  that constant before every engine (`turbo-rails`, `importmap-rails`, `action_text`) finished
  registering its own autoload paths, freezing the shared paths array before those engines could
  `unshift` onto it. Fixed by wrapping the assignment in `Rails.application.config.to_prepare do
  ... end`. **Any future initializer that references an autoloadable `app/` constant directly
  should be treated as suspect** if boot ever throws a frozen-array error again.
- **Real Twilio credentials don't exist in this environment**, so the Twilio adapter specs use
  hand-authored VCR cassettes built from Twilio's publicly documented response shape, not ones
  recorded from a real API call. **If real Twilio credentials are ever configured, these cassettes
  should be re-recorded.**
- **`config/environments/test.rb` had no `active_job.queue_adapter` override** — fixed as described
  above.
- Manually verified the async path end-to-end: `IssueOrderService` for a `both`-channel driver →
  `SendNotificationJob` picked up by the actual `worker` (Sidekiq) container, logs showed
  `TestAdapter` firing twice with the correctly composed pt-BR message.

## Phase 8 — Avo admin panel

This phase surfaced more real deviations from `docs/plan.md` than any prior one, because the
plan's Avo section was written against Avo 3's capabilities/API, and the gem that actually resolved
(flagged as a risk back in Phase 1) is Avo 4.0.11 — a genuinely different product in a few places.

### What was created

- **Mounted Avo at `/admin`** (not the gem's `/avo` default): `config.root_path = "/admin"` +
  `mount_avo` added to `routes.rb` by hand (the `avo:install` generator claims to add this route
  but doesn't).
- **Single-gate authentication**: `config.current_user_method = :current_user` +
  `config.authenticate_with { redirect_to main_app.root_path, alert: ... unless current_user&.admin? }`
  — `main_app.root_path` (not bare `root_path`) is required since Avo's own controller has its own
  engine-internal `root_path`.
- **`ApplicationPolicy`**: added `admin?` + six `avo_*` methods, all defaulting to `admin?` — every
  resource policy gets admin-only Avo access for free by inheritance.
- **Three new policies**: `UserPolicy`, `DriverTruckPolicy`, `UserRolePolicy`. **`RolePolicy`**
  additionally overrides `avo_create?`/`avo_destroy?` to `false` — `Role::KEYS` is fixed reference
  data; creating/destroying one from Avo would desync it or cascade-delete `user_roles`.
- **Avo resources**: `user.rb` (new — `password`/`password_confirmation` optional so editing a user
  without changing their password doesn't fail Devise's conditional validation, no `roles` field —
  see deviation below); `role.rb` (`key` made `readonly: true`); `user_role.rb` (**restored** after
  initially being deleted — became the actual mechanism for role assignment).

### Deviations discovered during execution

- **`avo-authorization` (Avo 4's Pundit integration) is a paid plugin, not on public RubyGems.**
  `docs/plan.md` assumed Avo 3's free, built-in Pundit integration. In Avo 4,
  `Avo.configuration.authorization_enabled?` requires the paid `avo-authorization` gem.
  **Discussed with the user and explicitly decided**: use a single gate only (admin-only mount
  access) rather than purchase a license. The Pundit scaffolding was kept anyway — dormant, ready
  to activate for free if the license is ever purchased, but harmless since only `admin` ever
  reaches `/admin` in the first place.
- **`bin/rails generate avo:install` claims to add the `mount_avo` route but doesn't** — possibly
  related to the file's CRLF line endings on this Windows checkout defeating the generator's

- **The Phase-8 Ferrum/RSpec timeout was a driver-name collision, not an RSpec/webmock

### Inline driver/truck registration on check-in

Previously, registering a new driver/truck and checking one in were three separate page visits.
Now the check-in page can do all three in one submission: the operator picks an existing
driver/truck from the dropdowns as before, or fills in "cadastrar novo motorista"/"cadastrar novo
caminhão" fields instead, and the new record(s) plus the visit are created together. The standalone
CRUD pages are unchanged.

**What changed**: `Visits::CheckInService` now wraps driver-save + truck-save + pairing + visit-
save in a transaction, with a `save_if_new` helper so it transparently accepts either an
already-persisted `driver:`/`truck:` or an unsaved `Driver.new(...)`/`Truck.new(...)` built from
form params — `raise ActiveRecord::Rollback` on any failed save undoes DB writes without clearing
`.errors`. Because Ruby passes objects by reference, the controller's `@new_driver`/`@new_truck`
and the service's `@driver`/`@truck` are the same objects, so validation errors land directly on
what the view already renders. Deliberately **no new "must pick one" validation code** — `Driver.new({})`/
`Truck.new({})` fail their own existing presence validations when neither the dropdown nor the
new-record fields are filled in (accepted tradeoff: 2-3 separate blank-field messages rather than
one combined message). New `app/views/shared/_errors.html.erb` extracted error-list markup that
was previously duplicated 3x, now used at 5 call sites. `accepts_nested_attributes_for` was
deliberately not used — `driver`/`truck` are independent, shared, pre-existing-or-not entities
referenced via `belongs_to`, not `Visit`-owned children.

**Gotcha**: two new request specs initially failed from the same "`let` evaluated too late" trap
documented in Phase 9 — referencing `driver.id` for the first time *inside* an
`expect { post ... }.not_to change(Driver, :count)` block triggers that `let`'s creation at that
exact point. Fixed by forcing eager evaluation before the `expect` block.

### Events ingestion base infrastructure

Design doc: `docs/events-plan.md`. Goal: let external devices — starting with a gate camera
reading license plates — push events into the app, without hard-wiring any one device straight
into domain logic. This phase built the generic pipeline only: a persisted `Event` record, a
machine-authenticated JSON ingestion endpoint, an event-type registry, and async processing via a

**What was created**: `events` table (`event_type`, `status` enum `pending`/`processed`/`failed`,
`device_id` plain string with no FK, `payload` jsonb — the schema's first JSONB column,
`received_at` kept distinct from `occurred_at` and `created_at`); new `api` namespace →

`TruckDetectedProcessor` stub. An unrecognized-but-present `event_type` still returns `202` and gets
persisted — the endpoint always accepts, failure is discovered async by the job (**accept-and-
fail-async**, a confirmed decision, not an oversight).

### Railway test-env deployment

Design doc: `docs/railway-deploy-plan.md`. Goal: a free, publicly reachable test/staging deployment
so the app can be demoed/verified without a local machine running — explicitly a throwaway test
env, not production. Live result:
`https://truck-load-queue-production.up.railway.app` (Railway project `adequate-analysis`).

**What was created/changed**: the `bin/*` executable-bit bug (flagged but left unfixed in the
events-ingestion round above) was a genuine deploy blocker — Railway builds straight from git's
stored file mode via the Dockerfile's `COPY . .`, so `ENTRYPOINT`/`CMD` would have hit
`permission denied` on the first deploy. Fixed via `git update-index --chmod=+x <files>`
immediately followed by `git commit`. Provisioned via the Railway dashboard (not config-as-code —
a repo-root `railway.toml`'s `startCommand` would conflict across the web/worker split): web
service with a blank Start Command (keeps `bin/docker-entrypoint`'s `db:prepare` intact), worker
service with Start Command `bundle exec sidekiq` (bypasses the entrypoint entirely — confirmed via
logs showing no migration output), plus Postgres/Redis plugins with public networking off.

**Deviations/gotchas discovered during execution**:
- **This Windows checkout cannot persist a Unix executable bit through the working tree at all**,
  and a background auto-checkpoint process made the failure mode worse. Even after
  `git update-index --chmod=+x` stages a `755` mode, any subsequent plain `git add`/GUI "stage all"
  re-derives the mode from the filesystem (always `644` here) and silently overwrites the staged
  `755` before it's committed. This happened twice — once via an automatic `--wip--` checkpoint
  commit, once via a manual stage-all. **The only sequence that reliably sticks**:
  `git update-index --chmod=+x <files>` immediately followed by `git commit`, with nothing else
  touching those files in between.
- **After PR #12's squash merge, the `bin/*` fix got lost a third time** — the squash's single-
  commit diff only included docs changes, not the mode fix, even though the pushed branch tip had
  it correct. Re-fixed directly on `main` (commit `ec8b8ae`). GitHub also auto-deleted
  `railway-deploy` after the merge, breaking Railway's auto-deploy trigger; resolved by pointing
  both Railway services at a new `test` branch. Also set `git config core.fileMode false` locally
  (this machine only) to eliminate the cosmetic `M` noise — side effect: any *future* permission
  change on this machine still needs the explicit chmod+commit sequence, since git no longer
  auto-detects a chmod from the filesystem at all.
- **Railway's "Custom Start Command" on a Dockerfile-deployed service overrides the image's
  `ENTRYPOINT` entirely (exec form), not just `CMD`** — exactly what makes the web/worker split
  work: blank Start Command keeps the entrypoint's `db:prepare` conditional intact, `bundle exec
  sidekiq` bypasses it completely.
- **Zero application code changes were needed for Railway's dynamic `PORT`/service networking** —
  `config/puma.rb`'s existing `ENV.fetch("PORT", 3000)` and Sidekiq's default Redis resolution both
  already picked up Railway's injected values.
- **Known, deliberately-accepted limitation**: `TWILIO_*` env vars left unset on both services —
  `config/initializers/notifications.rb` picks the adapter purely off `Rails.env.production?`, so

### Order number on visits

Previously "issuing an order" only stamped a timestamp (`order_issued_at`) used purely as the FIFO
sort key — no human-facing order number existed anywhere. Now a truck cannot enter the queue
without one: the expedition operator must type an order number when issuing an order, and the
registration operator may optionally supply one at check-in time, in which case the truck skips the
yard list entirely and goes straight into the queue (or straight to `loading`, if the queue is
empty) — same underlying service, reused.

**What changed**: nullable `order_number:string` column on `visits` (nullable because `in_yard`
visits don't have one yet); `validates :order_number, presence: true, unless: :in_yard?` on `Visit`
— this is what makes "no order number → can't be in the queue" an enforced DB-level invariant
rather than a UI convention (no uniqueness constraint — order numbers can repeat, confirmed with
the user). `Visits::IssueOrderService` gained a required `order_number:` kwarg.
`Visits::CheckInService` gained an optional `order_number: nil` kwarg — when given, it calls
`IssueOrderService` on the just-created visit inside the same transaction, rolling back the whole
check-in if issuance somehow fails. Views/Avo updated to surface the field.

**Gotcha worth remembering for future validations**: after a failed `ActiveRecord#update`, the
in-memory object still reflects the *attempted* (unsaved) attribute values (`assign_attributes`
runs before validation) — a spec asserting "the visit stayed `in_yard`" after a rejected issuance
must `visit.reload` first, or it sees the attempted `status: "queued"` instead of the actual,
unpersisted DB state.

### Live plate autofill on check-in from `truck_detected` events

A gate camera (HikCentral) sends `truck_detected` events with a plate to the events pipeline built
in the "Events ingestion base infrastructure" round above. That round's `TruckDetectedProcessor` was
a deliberate no-op stub; this round gives it a first real effect — pushing the detected plate live
onto the yard check-in screen — while still stopping short of creating a `Visit`, which remains
explicit future work.

The check-in screen (`registration/visits#index`) turned out to already be a single page (form +
yard list together, no separate "list" vs. "add form" screens), so the two scenarios originally
described collapsed into one implementation: whenever an operator has the page open, the plate field
is live-filled via Turbo Streams. Confirmed with the user: keep the single combined page (no new
screens/routes); auto-trigger the existing blur-lookup after filling the plate, so truck
model/capacity populate immediately if that truck is already registered; always overwrite whatever
is currently in the field, since the detection event is ground truth for who's at the gate right now.

**What changed**: `TruckDetectedProcessor#call` now normalizes `event.payload["plate"]` via
`Truck.normalize_value_for(:plate, ...)` and, if present, calls
`Turbo::StreamsChannel.broadcast_replace_to("registration_checkin", target: "truck_plate_field", ...)`
— the same broadcast primitive the public queue screen already uses, just from a job instead of a
model callback; a blank/missing plate just logs and no-ops rather than failing the event. The plate
label/input/spinner group was extracted out of the check-in form into
`app/views/registration/visits/_truck_plate_field.html.erb` (wrapped in `<div id="truck_plate_field">`)
so the exact same partial renders both the normal form field and the broadcast target — it uses
plain `label_tag`/`text_field_tag` rather than the `fields_for` builder so it can render outside the
form context, reproducing the same field name/id (`visit[truck][plate]` / `visit_truck_plate`) Rails'
`fields_for :truck` would generate. `index.html.erb` gained a `turbo_stream_from "registration_checkin"`
subscription, mirroring the public queue's `turbo_stream_from "public_queue"`.

To auto-trigger the existing lookup without disturbing normal page loads, `lookup_controller.js`
gained a `queryTargetConnected(target)` Stimulus lifecycle callback — it fires whenever a
`query`-target element is (re)inserted into the controller's scope, including via a Turbo Stream
replace, and calls `this.lookup()` only when that element carries `data-lookup-autofill="true"`. That
flag is set to `true` only on the broadcast-rendered partial (`autofill: true` local) and `false` on
the normal page render, so a fresh page load never fires a spurious lookup.

**Gotcha discovered during manual verification, then fixed**: `config/cable.yml`'s dev `async`
adapter only shares broadcasts within a single OS process, but `Events::ProcessEventJob` runs in the
separate `worker` Sidekiq container while the browser's Action Cable connection is served by `web` —
so a broadcast issued during a real `docker compose up` session never reached the browser, even
though the worker logs showed the job completing with no errors. Confirmed this wasn't a code defect
by temporarily pointing dev's cable adapter at the already-running Redis service, which made
cross-process delivery work correctly end-to-end (live fill, auto-lookup, and always-overwrite all
verified manually). Since Redis is already a dev dependency (used by Sidekiq), that temporary swap

### HikCentral ANPR event ingestion, filtered to real plate detections

The previous round's `/api/events` contract was a placeholder shape, since the real vendor payload
wasn't known yet. The user supplied HikCentral's actual webhook payload and the vendor's OpenAPI
guide (`docs/HikCentral Professional OpenAPI V3.1.1_Developer Guide...pdf`, confirmed via
`pdftotext` search: p.859 lists `eventType` `131622` as "License Plate Information Uploading",
p.813-816 documents the `OnEventNotify` envelope and ANPR `data` fields) — HikCentral pushes
`{method: "OnEventNotify", params: {sendTime, ability, events: [...]}, isHistory, event}`, where
each `events[]` entry has `eventType` (numeric — other codes exist for door/access/face/GPS events),
`srcIndex`/`srcType`/`srcName`, `happenTime`, `status`, and a `data` object whose `plateNo` is either
the detected plate or the literal string `"Unknown"` when the camera detects a vehicle but can't
read its plate.

Since more vendor integrations are expected later, this shape got its own ingestion path rather than
reshaping the generic contract: a new `POST /api/hikcentral/events` route, confirmed with the user
over folding vendor-detection logic into the existing generic endpoint. **What was created**:
`Api::Hikcentral::EventsController` (`< Api::BaseController`, reusing the existing Bearer-token
check unchanged) and `Events::Adapters::HikcentralAdapter` — the only place that knows HikCentral's
shape. The adapter reads `params.events[]`, drops (no `Event` row at all) any sub-event where
`eventType != 131622` **or** `data.plateNo == "Unknown"` (confirmed with the user as an OR — either
condition alone is enough to skip; skipped sub-events are pure noise from a live camera feed, not
worth an audit trail), and for each surviving sub-event calls the **existing, unmodified**
`Events::IngestEventService` with `event_type: "truck_detected"`, `device_id: srcIndex`,
`occurred_at: happenTime`, `payload: {"plate" => plateNo}`. This is the key design point: from
`Events::Registry`'s, `Events::ProcessEventJob`'s, and `TruckDetectedProcessor`'s point of view
(including the check-in live-autofill feature built on top of it in the previous round), a
HikCentral-originated event looks exactly like today's generic `truck_detected` event — none of
that pipeline needed to change. The generic `POST /api/events` endpoint and contract are untouched,
staying available as the landing contract any future vendor adapter (`/api/<vendor>/events`) can
feed into the same way.

**Gotcha caught by the request spec**: the adapter's first cut compared `eventType` with strict
Integer `==`, which passed when tested with real JSON but silently failed when a request spec posted
plain form-encoded params (Rails stringifies nested values, turning `131622` into `"131622"`) — every
event was wrongly skipped. Fixed with `.to_i` on the comparison for robustness, and the request spec
now sends `as: :json` to accurately match HikCentral's real `Content-Type: application/json` posts
rather than exercising a form-encoded path production traffic never takes.

```bash
docker compose run --rm -e RAILS_ENV=test web bundle exec rspec   # 224 examples, 0 failures
docker compose run --rm web bin/rubocop                          # clean except pre-existing offenses
```

Manually verified via `docker compose up`: POSTing the real example payload (`131622`, plate
`EZL3101`) → `202`, one `Event` created; POSTing a push containing a non-`131622` event and a
`131622`/`"Unknown"`-plate event → `202`, `skipped: 2`, `Event.count` unchanged; POSTing a
`131622`/registered-plate event while the check-in screen was open → Placa/Modelo/Capacidade filled
in live, same as the existing generic-endpoint path. `docs/example_payload_hikcentral.txt` (the raw
example payload the user supplied) was deleted once the adapter spec had its own inlined fixture
covering the same shape.

**Follow-up fix — auth header**: HikCentral's real event-push mechanism doesn't send the shared
secret via `Authorization: Bearer` (it doesn't support configuring that scheme) — it sends a plain
`Token` header instead. `Api::BaseController#authenticate_device!`'s inline
`Authorization`-header read was extracted into a `provided_token` method, which
`Api::Hikcentral::EventsController` overrides to read `request.headers["HTTP_TOKEN"]` — the generic
`/api/events` endpoint is untouched and still uses `Authorization: Bearer`.

**Gotcha while pinning down the exact header key**: Rack prefixes *every* incoming wire header with
`HTTP_` (uppercased, dashes to underscores) when building the request env — a wire header literally
named `Token` becomes env/`request.headers` key `HTTP_TOKEN`, but a wire header literally named
`HTTP_TOKEN` (as raw wire text) becomes the *double*-prefixed `HTTP_HTTP_TOKEN`. This was confirmed
empirically (temporary logging + `curl` against the running dev server) after an initial mix-up
where "the header name is HTTP_TOKEN" was first read as the literal wire text rather than as Rack's
already-prefixed env-key form — the user's own `request.headers.each` inspection of a real request
(showing key `"HTTP_TOKEN"`) confirmed the real device sends a wire header named `Token`, matching
the code as implemented. Verified with `curl -H "Token: <token>"` → `202`; missing/wrong `Token` →
`401`; `/api/events` with `Authorization: Bearer` unaffected.

### Feature flags structure

Different client deployments will need different behaviors — the concrete driver: after a truck is
registered, the app should call the HikCentral API to add the plate to an access list, but only for
clients that actually have HikCentral/Hikvision hardware. Since each client is its own single-yard
deployment (not multi-tenancy), this only needed a small number of per-install capability switches,
not a full flagging platform.

**What was created**: `FeatureFlag` (`app/models/feature_flag.rb`), backed by a new `feature_flags`
table (`key` unique string, `enabled` boolean defaulting `false`). `FeatureFlag::KEYS` is the
whitelist of valid keys (`%w[hikcentral]` so far), following the same fixed-reference-data pattern
as `Role::KEYS`. `FeatureFlag.enabled?(:key)` raises `ArgumentError` on a key not in `KEYS` — a
typo at a call site or in a console session is caught immediately rather than the integration
silently never firing. `FeatureFlag.enable!(:key)`/`.disable!(:key)` find-or-initialize a row and
persist it.

**Deliberately excluded, after discussion with the user**: no seed data (a valid key with no row
defaults to disabled, so there's nothing to keep in sync with `KEYS`) and no Avo/admin UI. Toggling
is done exclusively via `bin/rails console` — this was a specific choice to prevent an admin from
accidentally flipping an integration off/on through a UI click, while still letting ops flip it
instantly during an incident with no redeploy (the alternative considered and rejected: an
ENV-var-driven flag mirroring `config/initializers/notifications.rb`'s adapter-selection pattern,
which would require a redeploy to change).

This round only built the flag scaffold — the actual HikCentral "add plate on truck registration"
API call is separate future work, to be planned once needed.

### HikCentral outbound vehicle-list sync on check-in

This closes the loop the "Feature flags structure" round above anticipated but deliberately left
unbuilt: after a truck checks in, and only when `FeatureFlag.enabled?(:hikcentral)`, the app now
calls HikCentral's OpenAPI to add the truck's plate to a vehicle list (an access whitelist a gate/
ANPR camera checks against), the same vendor referenced by the inbound ANPR-ingestion round above
— but this is the first **outbound** call to HikCentral; everything before this synced data the
other direction (HikCentral → app).

Per the vendor's OpenAPI guide (`docs/HikCentral Professional OpenAPI V3.1.1_Developer
Guide...pdf`, "Manage Vehicles" p.47-49, full request/response spec p.257-260), the relevant call is
`POST /artemis/api/resource/v1/vehicle/single/add`, authenticated with HikCentral's AK/SK
HMAC-SHA256 request signing (doc §3.2) — a scheme with no existing precedent in this repo (the
inbound webhook side only *validates* a shared-secret `Token` header on incoming requests; it never
signs outgoing ones), and no HTTP client gem beyond `twilio-ruby` (Twilio-specific), so this was
built on stdlib `Net::HTTP` rather than adding a new dependency.

**Decisions made with the user before implementing**: sync once per **truck** (not per visit) —
skip the API call if that truck was already synced, tracked via a new `trucks.hikcentral_synced_at`
timestamp, rather than re-adding/updating the same plate on every repeat visit; a long-lived
validity window (`effectiveDate` = now, `expiredDate` = 5 years out, no renewal/removal logic — same
"explicitly out of scope for now" treatment as visit cancellation); and sending the driver's name
and phone (`personGivenName`/`phoneNo`) in addition to the plate, so the vendor's vehicle record is
identifiable to yard/security staff reviewing HikCentral's own UI.

**What was created**:
- `trucks.hikcentral_synced_at` (datetime, nullable) — the per-truck "already added" marker,
  following the same timestamp-per-milestone convention as `Visit`'s `entered_yard_at`/
  `order_issued_at`/etc.
- `Hikcentral::Client` (`app/services/hikcentral/client.rb`) — builds the AK/SK-signed request
  (Content-MD5, Content-Type, Date, `X-Ca-Key`, `X-Ca-Timestamp`, `X-Ca-Signature`) and posts JSON
  to `vehicle/single/add`, raising `Hikcentral::Client::RequestError` on a non-2xx HTTP response or
  a parsed body `code != "0"` (HikCentral's own success/failure signal, independent of HTTP status).
  Credentials (`HIKCENTRAL_BASE_URL`/`APP_KEY`/`APP_SECRET`/`VEHICLE_GROUP_INDEX_CODE`/
  `OPERATOR_USER_ID`) default from `ENV`, mirroring `TwilioSmsAdapter`'s constructor pattern — added
  to `.env.example` with the same "placeholder, confirm against the real instance" caveat already
  used for the inbound events contract, since `vehicleGroupIndexCode` names a vehicle list that has
  to already exist on the HikCentral side.
- `Hikcentral::AddVehicleService` (`.enqueue`/`#call`) + `Hikcentral::AddVehicleJob` — mirrors
  `Notifications::NotifyDriverService`/`SendNotificationJob` exactly: `.enqueue(truck:, driver:)`
  enqueues the job; the job re-checks `hikcentral_synced_at.nil?` (defensive against a duplicate
  enqueue) before calling the service, which calls the client and marks the truck synced on success.
  Same `queue_as :default`, `retry_on StandardError, wait: :polynomially_longer, attempts: 5` as
  every other job in the app.
- `Visits::CheckInService#call` now enqueues the sync job after a successful check-in, guarded by
  `FeatureFlag.enabled?(:hikcentral) && truck.hikcentral_synced_at.nil?` — same "guarded enqueue
  after a state change, from the service, not a model callback" shape `IssueOrderService` already
  uses for its notification trigger.

**Testing note**: no VCR cassette (unlike the Twilio adapters) — there's no real HikCentral sandbox
to record a cassette against, so `Hikcentral::Client`'s spec stubs the HTTP call directly with
WebMock instead, asserting the signed headers and request body shape.

**Gotcha while writing the service spec**: asserting `expired_date - effective_date == 5.years`
(or `be_within(1).of(5.years)`) fails intermittently — `Time#+ 5.years` advances the calendar
correctly (accounting for however many real leap days fall in that span), so the actual elapsed
seconds vary by up to a day or two from `5.years.to_i`'s fixed 365.25-day-average conversion. Fixed
by widening the tolerance to `be_within(3.days.to_i)`.

**Follow-up — generic integrations config**: `Hikcentral::Client` initially read its 5 settings
straight from `ENV`, matching the Twilio adapters. The user asked for this to go through a config
YAML instead, generalized so future integrations can share the same file/class rather than each
inventing its own — `config/integrations.yml` (one `default: &default` anchor, a `hikcentral:`
section, each value still ERB-pulled from the same `ENV["HIKCENTRAL_*"]` vars, per-env `<<: *default`
like `config/database.yml`) plus `Integrations::Config` (`app/services/integrations/config.rb`),
whose `.for(name)` is the only call site `Hikcentral::Client`'s constructor now defaults from.
**Gotcha caught by a quick `bin/rails runner` probe before writing the class**: `Rails.application
.config_for` only gives dot-access at the *top* level of the YAML — a nested section like
`hikcentral:` comes back as a plain symbol-keyed `Hash`, not something `.base_url`-callable. `.for`
re-wraps that section in `ActiveSupport::OrderedOptions` (the same class Rails itself uses for the
top level) to get the same dot-access one level down. Raises `Integrations::Config
::UnknownIntegrationError` for a name not in the file, mirroring `FeatureFlag`'s
raise-on-unknown-key style.
